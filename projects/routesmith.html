PROJECT 02 · AI INFRASTRUCTURE

RouteSmith智路网关

基于 Java 17 与 Spring WebFlux 的多模型治理网关。统一 OpenAI / Anthropic 协议，并以请求感知路由、延迟 SLO、故障转移和审计台账承接 Agent 应用的模型访问。

01 / PROBLEM

为什么需要网关

当多个 Agent 直接接入不同模型服务时，协议适配、凭证、重试和成本逻辑会散落在业务代码中。模型切换会扩大改动范围，也难以统一追踪一次请求经过了哪个模型、花费多少、为何降级。

问题RouteSmith 的处理
OpenAI / Anthropic 请求格式不同协议适配层统一消息、流式事件与 Tool Use
上游限流或服务异常健康检查、冷却、重试和候选模型故障转移
团队成本难以控制Scoped API Key、团队配额、预算预留与结算
02 / FLOW

可解释路由链路

业务侧只依赖兼容协议。RouteSmith 先抽取输入/输出规模、Tool、流式模式、客户端协议与延迟 SLO，按上下文窗口和能力过滤候选，再结合 Provider 单价、Prefill/Decode 吞吐、EWMA 延迟和可靠性完成请求级排序。

兼容入口OpenAI Chat / Anthropic Messages
请求治理API Key / 限流 / 幂等 / 预算
请求感知路由能力过滤 / 成本延迟预测 / SLO
Provider AdapterTool Call / SSE / 协议转换
结算与证据SQL Ledger / Health / Trace
03 / RELIABILITY

故障与额度边界

  • Provider 连续失败达到阈值后打开熔断器；429、5xx、超时和流打开前断连可切换至下一候选。
  • 满足延迟 SLO 的候选优先排序，超限候选仍保留为故障兜底并标记未命中；全部不满足时按 best-effort 返回。
  • 同协议 SSE 按首包目标路由；跨协议需要缓冲并合成事件，按完整生成耗时估算，避免系统性低估延迟。
  • 路由计划是有限有序列表，每个候选最多尝试一次，避免级联故障下的重复调用与无限重试。
  • token 预算按用户请求预留一次，跨 Provider fallback 不重复占用；成功按真实 usage 结算，失败释放。
  • 客户端 API Key 与上游 Provider 密钥隔离；幂等缓存和 SQL 用量账本保证重放请求不重复计费。
  • 流式响应开始后不再切换模型，避免客户端收到重复或语义不一致的 token。
